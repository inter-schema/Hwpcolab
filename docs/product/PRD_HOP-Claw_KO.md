## 1. 문서의 목적과 적용 범위

이 문서는 HOP-Claw가 누구의 어떤 문제를 해결해야 하는지, 제품이 제공할 가치와 성공 기준은 무엇인지, 어느 범위까지 제품으로 책임질 것인지를 정의한다.

이 문서는 기능설계서(Functional Specification)가 아니다. 화면 배치, 컴포넌트 상태, API 시그니처, 내부 데이터 스키마, 알고리즘, 오류 코드, 세부 테스트 케이스를 확정하지 않는다. 그러한 내용은 이 PRD의 요구사항을 입력으로 삼아 별도 기능설계서와 기술설계서에서 정의한다.

### 1.1 문서 간 역할 구분

| 문서 | 답해야 하는 질문 | 주요 독자 | 포함하는 내용 |
|---|---|---|---|
| **PRD(본 문서)** | 왜 만들며, 누구를 위해, 어떤 결과를 달성해야 하는가? | 제품 책임자, 설계자, 개발자, QA, 피칭 검토자 | 사용자 문제, 가치 제안, 목표, 제품 범위, 우선순위, 성공 지표, 제약 |
| **기능설계서** | 사용자가 기능을 어떻게 사용하며 시스템은 각 상황에서 어떻게 동작하는가? | 디자이너, 프런트엔드·백엔드 개발자, QA | 사용자 흐름, 화면·상태, 상호작용, 권한·승인, 예외·복구, 수용 테스트 |
| **기술설계서** | 요구 기능을 어떤 구조와 기술로 구현하고 운영하는가? | 아키텍트, 개발자, 보안·운영 담당자 | 아키텍처, 모듈 경계, 어댑터 계약, 데이터 모델, API, 기술 선택, 성능·보안 설계 |

기능설계서와 기술설계서는 PRD의 요구사항 ID를 참조해야 한다. 하위 문서에서 제품 목표나 범위를 변경해야 한다면 PRD 변경 이력을 함께 갱신한다.

## 2. 제품 개요

### 2.1 제품 정의

HOP-Claw는 Windows 데스크톱에서 HWP/HWPX 문서를 열고, 작성하고, 편집하고, 검토할 수 있도록 돕는 사람-AI 협업 문서 작업실이다. 사용자는 자연어로 작업을 지시하고, AI는 문서 구조를 바탕으로 편집 변경안을 제안한다. 사용자는 변경 전후를 검토하고 필요한 항목만 수락하거나 거부한다.

제품의 다음 단계는 단순한 AI 문장 편집을 넘어, 한국어 문서 형식에 강점을 둔 **검증 가능한 문서 상호운용 작업실(Verifiable Document Interoperability Workbench)**로 발전하는 것이다. HWP/HWPX를 중심에 두되 DOCX, XLSX, PDF 등 외부 형식과의 자료 활용 및 변환 과정에서 구조 보존 여부와 손실 가능성을 사용자에게 설명해야 한다.

### 2.2 제품 비전

> 한국어 문서 작업자가 형식과 도구의 제약에 갇히지 않고, AI가 제안한 변경과 변환 결과를 이해하고 검증하면서 신뢰할 수 있는 문서를 완성하도록 돕는다.

### 2.3 제품 포지셔닝

- **핵심 제품:** HWP/HWPX 문서의 로컬 작성·편집·검토를 위한 데스크톱 애플리케이션
- **차별화 방향:** 문서 구조를 이해하는 편집, 변경 단위 검토, 형식별 변환 품질 설명, 개인정보 전송 통제
- **AI의 역할:** 사용자의 의도를 해석하고 작업을 계획하며, 도구 실행 결과를 설명하고 검토를 돕는 협업자
- **결정 원칙:** 파일 형식 변환과 문서 편집의 정확성은 결정론적 엔진과 검증 절차가 책임진다. LLM의 자연어 생성만으로 바이너리·패키지 변환의 정확성을 보장하지 않는다.

## 3. 문제 정의

### 3.1 사용자가 겪는 핵심 문제

1. **한국어 문서 형식의 장벽:** HWP/HWPX 문서는 일반적인 텍스트 파일과 다르며, 표·스타일·쪽 구성·개체 관계를 유지하면서 다른 형식과 주고받기 어렵다.
2. **AI 편집 결과의 불투명성:** AI가 문서 전체를 다시 쓰거나 변경 위치를 명확히 제시하지 않으면, 사용자는 무엇이 바뀌었는지와 기존 내용이 훼손되었는지 판단하기 어렵다.
3. **자료 재사용의 단절:** PDF, DOCX, XLSX 등의 자료에서 정보를 가져올 수는 있어도, 추출과 편집 가능한 구조의 보존, 원문 근거 추적, 대상 문서 반영은 서로 다른 문제다.
4. **레이아웃 품질 확인의 부담:** 문장 수정만으로 끝나지 않는다. 표 너비, 셀 잘림, 쪽 나눔, 글꼴 대체 등 실제 출력 결과를 확인해야 한다.
5. **개인정보 전송에 대한 불안:** 로컬 문서 처리와 원격 AI 추론은 다르다. 사용자는 어떤 내용이 어떤 공급자에게 전달되는지, 마스킹이 어느 수준까지 적용되는지 알아야 한다.

### 3.2 현재 제품 기반과 남은 간극

공개 README의 v0.2.3 설명에 따르면 현재 제품은 HWP/HWPX 열기·편집·저장, 빈 문서 작성, AI 변경 제안 및 Diff 검토, 표 구조 편집, 레이아웃 측정과 시험 편집, 작성 선호사항, 다양한 AI 공급자 연결을 제공한다. 참고자료 입력에는 DOCX·XLSX·PDF 등이 포함되지만, README가 설명하는 처리 방식은 주로 텍스트·표 추출이다.

따라서 다음을 동일한 수준의 기능으로 표현해서는 안 된다.

- 파일에서 텍스트를 추출하는 기능
- 원본의 구조와 서식을 보존하는 편집 기능
- 다른 형식으로 변환하는 기능
- 변환 결과를 독립적으로 검증하는 기능

제품은 현재 제공 기능과 향후 목표 기능을 구분해 사용자에게 알려야 한다. 특히 다중 형식 읽기 지원을 완전한 양방향 변환 지원으로 오해하게 해서는 안 된다.

## 4. 대상 사용자와 사용 맥락

### 4.1 핵심 사용자군

| 사용자군 | 주요 작업 | 가장 큰 불편 | 기대 가치 |
|---|---|---|---|
| 공공·행정 문서 작성자 | 공문, 계획서, 보고서, 회의자료 작성·수정 | HWP 양식과 서식을 유지하며 반복 수정해야 함 | 구조와 서식을 유지하는 빠른 편집, 변경 이력 확인 |
| 기업·기관 실무자 | 제안서, 내부 보고서, 계약·운영 문서 검토 | 여러 파일의 내용을 취합하고 표와 레이아웃을 맞춰야 함 | 자료 기반 작성, 표 편집, 결과 검증 |
| 연구·교육 종사자 | 연구 보고서, 강의자료, 평가 문서 작성 | PDF·DOCX·Excel 자료를 한국어 문서에 재사용하기 어려움 | 근거가 연결된 자료 반영, 구조화된 문서 작성 |
| 고급 문서 사용자 | 복잡한 표·쪽 구성·스타일이 포함된 문서 편집 | 작은 수정도 전체 레이아웃을 깨뜨릴 수 있음 | 정밀한 변경 단위 제어와 레이아웃 검증 |

### 4.2 주요 사용자 과업(Jobs to Be Done)

- 기존 HWP/HWPX 문서의 일부만 고치고 나머지 형식과 내용을 보존하고 싶다.
- 여러 참고자료를 읽고 핵심 내용을 출처와 함께 기존 문서에 반영하고 싶다.
- AI가 변경한 부분을 적용 전에 비교하고, 필요한 변경만 선택하고 싶다.
- 표나 페이지 레이아웃이 망가지지 않았는지 수정 전후로 확인하고 싶다.
- 민감한 문서를 원격 AI에 보내기 전에 전송 내용을 확인하고 통제하고 싶다.
- DOCX·XLSX·PDF와 HWP/HWPX 사이에서 가능한 범위와 손실을 알고 안전하게 작업하고 싶다.

### 4.3 핵심 사용 시나리오

**시나리오 A: 기존 공문서 수정**  
사용자가 기존 HWP 문서를 열고 문체 통일과 일부 문단 수정을 요청한다. 제품은 변경안을 제시하고, 사용자는 문단별로 수락·거부한 뒤 레이아웃을 확인하고 저장한다.

**시나리오 B: 참고자료 기반 보고서 작성**  
사용자가 HWPX 양식과 PDF 사업계획서, XLSX 예산표를 제공한다. 제품은 지원 범위 안에서 내용을 추출하고 출처 위치를 연결해 초안을 작성한다. 추출할 수 없거나 의미가 불확실한 정보는 추측하지 않고 검토 대상으로 남긴다.

**시나리오 C: 형식 변환 및 결과 검토**  
사용자가 HWPX를 DOCX로 내보내려 한다. 제품은 지원되는 요소와 변환될 요소를 사전에 설명하고, 변환 후 구조·텍스트·패키지·렌더링 검증 결과를 보여준다. 검증에 실패하거나 손실이 큰 경우 성공으로 표시하지 않고 사용자의 결정을 기다린다.

**시나리오 D: 민감정보가 포함된 문서 작업**  
사용자가 원격 AI 공급자를 선택한다. 제품은 전송될 문서 범위와 감지된 민감정보, 제외 영역, 마스킹의 한계를 보여주고, 사용자가 검토한 뒤 전송하도록 한다.

### 5.2 비목표

- 여러 사용자가 동시에 같은 문서를 편집하는 실시간 온라인 공동 편집 서비스 제공
- 모든 HWP/HWPX/DOCX/XLSX/PDF 문서의 완전한 무손실 상호변환 보장
- LLM이 임의의 바이너리 파일이나 패키지를 직접 재작성하도록 허용
- 전문 DTP·출판 도구 수준의 페이지 조판 및 그래픽 편집 대체
- 모든 AI 공급자의 데이터 보관·학습 정책을 제품이 대신 보증
- 이미지 첨부 기능만으로 모든 스캔 문서와 손글씨를 완벽하게 구조화
- 사용자가 검토하지 않은 고위험 변경을 기본값으로 자동 적용

## 6. 제품 원칙

1. **원본 보호:** 변환과 대규모 편집은 원본을 덮어쓰지 않는 별도 결과물에서 수행한다.
2. **명시적 지원 범위:** 형식·기능별로 지원 수준을 표시하며, 미지원 기능을 조용히 삭제하거나 변형하지 않는다.
3. **검증 가능한 결과:** 성공 여부는 도구 실행 종료 코드가 아니라 독립 검증 결과로 판단한다.
4. **사용자 승인 우선:** 의미·서식 손실이 있거나 되돌리기 어려운 작업은 적용 전에 설명하고 승인을 받는다.
5. **근거 추적:** 참고자료에서 가져온 주요 정보는 가능한 범위에서 원본 파일과 위치를 추적할 수 있어야 한다.
6. **개인정보 투명성:** 로컬 처리, 원격 전송, 가명처리, 비가역적 삭제를 구분해 표시한다.
7. **점진적 확장:** 형식 지원은 구현량이 아니라 검증된 사용 시나리오와 회귀 테스트를 기준으로 확대한다.
8. **접근 가능한 검토:** 색상만으로 상태를 전달하지 않으며 키보드 조작과 명확한 포커스·레이블을 지원한다.

## 7. 제품 요구사항

요구사항 우선순위는 MoSCoW 기준으로 구분한다. Must는 제품 신뢰성을 위해 필수이며, Should는 핵심 사용성을 높이는 요구사항, Could는 후속 확장 요구사항이다.

### 7.1 문서 작성·편집

| ID | 요구사항 | 우선순위 | 사용자 가치 |
|---|---|---|---|
| PR-ED-01 | 사용자는 빈 HWP/HWPX 문서를 만들고 제목·본문·목록·표를 작성할 수 있어야 한다. | Must | 신규 문서 작성 |
| PR-ED-02 | 사용자는 기존 문서 전체 또는 선택 영역을 대상으로 자연어 편집을 요청할 수 있어야 한다. | Must | 기존 문서 재작업 감소 |

## 9. 범위와 단계별 출시 전략

### 9.1 P0: 신뢰성 기반 강화

**목표:** 기존 HWP/HWPX 편집 경험을 안정화하고 제품의 신뢰 경계를 명확히 한다.

포함 범위:
- 현재 HWP/HWPX 편집·저장 기능의 회귀 테스트 확대
- 문서 변경 Diff의 안정적인 위치 연결과 원본 보호
- 형식별 지원 기능 및 제한사항 정리
- 참고자료 추출 결과의 출처 위치와 실패 상태 표시
- 개인정보 전송 전 확인 및 제외 영역 UX 강화
- 악성 압축 파일과 비정상 문서 입력에 대한 방어 테스트

완료 조건:
- 핵심 편집 시나리오에 자동 회귀 테스트가 존재한다.
- 실패·취소·검증 오류에서 원본 문서가 변경되지 않는다.
- 사용자가 AI 전송 범위와 마스킹 상태를 확인할 수 있다.
- README의 기능 설명이 실제 동작과 일치한다.

### 9.2 P1: 문서 검토와 상호운용성 확장

**목표:** DOCX·XLSX·PDF를 단순 첨부 자료가 아니라 명시된 지원 수준을 가진 작업 입력·출력으로 확장한다.

포함 범위:
- DOCX 구조 인식 및 제한된 변환 시나리오
- XLSX 읽기·검토 기능의 의미 보존 범위 명시
- PDF 내보내기와 텍스트 기반 가져오기 경로 분리
- 변환 전후 비교와 변환 결과 보고서
- 구조·패키지·텍스트·렌더링 검증 자동화
- Diff에서 표·서식·페이지 변화의 구분 강화

완료 조건:
- 각 형식별 지원 매트릭스와 제한사항이 공개되어 있다.
- 지원 시나리오별 fixture와 독립 검증이 통과한다.
- 변환 결과에 보존·변환·평탄화·미지원 항목이 보고된다.
- 검증 실패 시 결과가 성공으로 노출되지 않는다.

**목표:** 복잡한 문서와 고급 업무를 대상으로 지원 범위를 확대한다.

- 복잡한 개체·필드·추적 변경 등 DOCX 고급 요소 지원
- 변환 품질 벤치마크와 호환성 리포트 자동 생성

P2의 세부 범위는 P0/P1의 품질 지표와 실제 사용자 수요를 평가한 뒤 결정한다.

## 10. 제약과 가정

### 10.1 확인된 제품 제약

- 현재 제품의 공개 배포 기준은 Windows 10/11 64-bit다.
- 데스크톱 앱은 Tauri v2, React 19, TypeScript 기반으로 설명되어 있다.
- HWP/HWPX 렌더링·편집은 @rhwp/core WASM 및 claw-hwp Node.js 사이드카 기반이다.
- PDF 텍스트 추출은 README 기준 최대 30페이지 제한이 있다.
- 첨부 파일 크기는 파일당 최대 128 MiB로 안내되어 있다.
- 원격 AI 공급자를 선택하면 문서에서 추출한 내용이 공급자 서버로 전송될 수 있다.
- 실시간 다중 사용자 공동 편집은 현재 제품 범위에 포함되지 않는다.

### 10.2 제품 기획 가정

- HWP/HWPX는 당분간 제품의 핵심 차별화 형식으로 유지한다.
- 다른 형식의 지원은 HWP/HWPX 편집 품질을 희생하지 않는 범위에서 단계적으로 확장한다.
- 사용자는 변환 성공 여부뿐 아니라 어떤 요소가 달라졌는지 설명받기를 원한다.
- 사용자는 모든 변환을 무조건 자동 적용하는 것보다 검토 가능한 결과를 선호한다.
- LLM 공급자와 모델에 따라 도구 호출·문맥 길이·비용·데이터 정책이 다르므로 공급자 중립적 정책 계층이 필요하다.

위 가정은 사용자 조사, 지원 요청, 제품 사용 데이터로 검증해야 한다.

| 기능 범위의 과도한 확대 | 핵심 편집 경험의 품질 저하 | 단계별 출시와 지표 기반 우선순위 조정 |

## 12. 제품 승인 및 출시 기준

제품 기능은 다음 조건을 만족해야 출시 후보에 포함할 수 있다.

1. 해당 기능이 하나 이상의 사용자 문제와 PRD 요구사항 ID에 연결되어 있다.
2. 지원 형식과 제한사항을 사용자가 이해할 수 있게 안내한다.
3. 원본 문서와 사용자의 데이터가 실패·취소 상황에서 보호된다.
4. 핵심 성공 경로와 실패 경로를 자동 테스트로 검증한다.
5. 개인정보 전송 경로와 사용자 승인 조건을 점검한다.
6. 문서 저장·변환 결과를 다시 열어 확인하는 검증 절차가 있다.
7. 사용자 문서와 릴리스 노트가 실제 동작과 일치한다.
8. 중대한 결함이 남아 있으면 출시를 차단하거나 제한사항을 명확히 공개한다.

## 13. 기능설계서로 넘길 항목

다음 항목은 본 PRD에서 제품 요구로만 정의했으며, 기능설계서에서 구체화해야 한다.

- 새 문서 작성, 기존 문서 열기, 저장 및 다른 이름으로 저장의 화면 흐름
- AI 작업 요청, 작업 진행 상태, 취소, 재시도 및 승인 흐름
- Diff 목록·상세 비교·필터·수락·거부·복구의 상호작용
- 참고자료 첨부, 파싱 상태, 출처 위치, 추출 실패 상태 표시
- 형식별 변환 설정, 사전 지원 범위 안내, 결과 보고서와 검증 실패 처리
- 개인정보 감지 결과, 마스킹 미리보기, 제외 영역, 원격 전송 확인
- 레이아웃 진단, 시험 적용, 전후 측정 결과와 경고 표시
- 키보드 접근성, 포커스 이동, 오류 메시지, 빈 상태 및 로딩 상태

기능설계서는 각 흐름에 대해 정상·경계·실패 상황을 정의하고, 본 문서의 요구사항 ID와 수용 기준을 연결해야 한다.
